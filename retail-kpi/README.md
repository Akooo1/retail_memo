# retail-kpi: синтетическая розничная витрина

> **СИНТЕТИЧЕСКИЕ ДАННЫЕ.** Все клиенты, имена, суммы и KPI в этой папке сгенерированы
> программой со случайным, но фиксированным seed. Ни один реальный клиент, счёт или
> транзакция не использовались. Маркировка: `client_id` вида `SYN-000123`, имена с
> префиксом `[SYN]`, колонка `is_synthetic = True` в каждой таблице. Название банка
> нигде не указывается намеренно.

Проект генерирует синтетических клиентов розничного банка (суммы в UZS), собирает из них
витрину «клиент × месяц», сегментирует клиентов на Mass / Affluent / Premium, считает KPI
по месяцам и сегментам, а затем готовит агрегированный вход для LLM, которая пишет
черновик комментария к KPI. Сам вызов LLM в проект не входит. Бизнес-обоснование и
границы этого AI-сценария описаны в [`../usecase-final.md`](../usecase-final.md).

## Быстрый старт

Нужен Python 3.13 (именно на нём проверяется CI).

```bash
cd retail-kpi
python3 -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m retail_kpi --out build     # ~2 секунды, 5 000 клиентов x 12 месяцев
pytest                               # все тесты должны быть зелёными
```

Параметры командной строки: `--out` (папка результатов, по умолчанию `build`),
`--seed` (по умолчанию 2025), `--clients` (5000), `--months` (12, минимум 4).

## Как проверить повторяемость

Витрина считается повторяемо, если два прогона с одинаковыми параметрами дают
одинаковые байты во всех файлах:

```bash
python -m retail_kpi --out build_a
python -m retail_kpi --out build_b
diff -r build_a build_b && echo "идентично"
```

`build/manifest.json` содержит SHA-256 каждого файла, параметры прогона и версии
Python, numpy и pandas. Это позволяет сравнить прогоны, сделанные на разных машинах,
без пересылки самих CSV. Тест `test_default_run_is_byte_identical` проверяет то же самое
автоматически.

Что гарантирует повторяемость:

1. **Один генератор случайных чисел.** Все случайные величины берутся из одного
   `numpy.random.Generator(seed)` в фиксированном порядке.
2. **Целые суммы.** Суммы в UZS округляются до целых, а доли до 4 знаков, поэтому
   форматирование чисел с плавающей точкой не влияет на байты CSV.
3. **Точные версии.** `requirements.txt` фиксирует версии пакетов. numpy не обещает
   одинаковый поток случайных чисел между версиями, поэтому на других версиях числа
   могут отличаться. Внутренняя согласованность витрины при этом сохраняется.

## Данные

### `data/clients.csv`: один синтетический клиент на строку

| Колонка | Тип | Смысл |
|---|---|---|
| `client_id` | str | `SYN-000001` … `SYN-005000` |
| `display_name` | str | `[SYN] Фамилия Имя`, случайное сочетание из коротких списков |
| `declared_income_uzs` | int | заявленный месячный доход, UZS |
| `is_synthetic` | bool | всегда `True` |

Имена есть только в этом файле. В витрину, KPI и вход для LLM они не попадают, и это
проверяется тестами.

### `data/products.csv`: один продукт клиента на строку

| Колонка | Тип | Смысл |
|---|---|---|
| `client_id` | str | ссылка на `clients.csv` |
| `product_type` | str | `card`, `deposit` или `loan` |
| `open_month` | `YYYY-MM` | месяц открытия, может быть до начала периода |
| `close_month` | `YYYY-MM` / пусто | месяц закрытия; пусто = продукт открыт |
| `is_synthetic` | bool | всегда `True` |

### `data/transactions_monthly.csv`: клиент × месяц, агрегаты операций

| Колонка | Тип | Смысл |
|---|---|---|
| `client_id`, `month` | str | ключ; у каждого клиента есть все месяцы |
| `txn_count` | int | число операций за месяц (0 = неактивен) |
| `txn_volume_uzs` | int | оборот за месяц, UZS |
| `end_balance_uzs` | int | остаток на конец месяца, UZS |
| `is_synthetic` | bool | всегда `True` |

### `mart/client_month.csv`: витрина

Колонки из `transactions_monthly` плюс:

| Колонка | Смысл |
|---|---|
| `declared_income_uzs` | из `clients.csv` |
| `avg_balance_3m_uzs` | средний остаток за этот и 2 предыдущих месяца (в начале периода берётся сколько есть) |
| `segment` | Mass / Affluent / Premium, см. «Сегментация» |
| `is_active` | `txn_count > 0` |
| `dormant_3m` | 3 месяца подряд без операций, включая текущий; пусто в первые 2 месяца |
| `in_churn_base` | в прошлом месяце клиент не был `dormant_3m`, то есть мог «уйти» в этом; пусто, если прошлый месяц не определён |
| `new_churn` | клиент стал `dormant_3m` именно в этом месяце |
| `has_card`, `has_deposit`, `has_loan` | продукт открыт в этом месяце (месяц закрытия считается закрытым) |
| `n_products` | число открытых продуктов |
| `is_synthetic` | всегда `True` |

## Сегментация

Сегмент определяется заново в каждом месяце и равен **старшему** из двух уровней.
Пороги включительные, все значения в UZS, задаются в `config.py`:

| Сегмент | Средний остаток за 3 мес. | или | Заявленный доход в месяц |
|---|---|---|---|
| Premium | ≥ 150 000 000 | | ≥ 40 000 000 |
| Affluent | ≥ 25 000 000 | | ≥ 15 000 000 |
| Mass | иначе | | иначе |

Активность в сегмент не входит и считается отдельным KPI. Если бы она входила,
отток и сегмент смешались бы в одну величину.

## KPI

Файл `mart/kpi_monthly.csv` содержит одну строку на (месяц, сегмент) и строку `ALL` на
месяц. Если в сегменте нет клиентов, строки для него нет. **Пустая ячейка означает «не
определено», а не ноль.**

| KPI | Формула | Пусто, когда |
|---|---|---|
| `clients` | число строк витрины | — |
| `active_clients` | число `is_active` | — |
| `active_share` | `active_clients / clients` | — |
| `dormant_3m_share` | доля `dormant_3m` | первые 2 месяца |
| `churn_rate` | `new_churn` / число `in_churn_base` | первые 3 месяца |
| `avg_balance_uzs`, `median_balance_uzs` | среднее и медиана `end_balance_uzs` | — |
| `txn_count_per_active` | `sum(txn_count) / active_clients` | нет активных |
| `txn_volume_per_active_uzs` | `sum(txn_volume_uzs) / active_clients` | нет активных |
| `products_per_client` | среднее `n_products` | — |
| `card_penetration`, `deposit_penetration`, `loan_penetration` | доля клиентов с открытым продуктом | — |

`mart/segment_migration.csv` показывает, сколько клиентов перешли из сегмента в первом
месяце в сегмент в последнем: `clients`, `share_of_from` (доля исходного сегмента) и
`direction` (`up`, `down` или `stable` по рангу Mass < Affluent < Premium).

## Функции

Ниже описана каждая функция пакета. Тест `test_readme_documents_every_function` падает,
если в коде появляется функция, которой нет в этом разделе.

### `generate.py`: генератор CSV

- **`month_labels(start, n_months)`** возвращает список месяцев `YYYY-MM` подряд от
  `start`. Корректно переходит через границу года.
- **`make_client_ids(n_clients)`** возвращает идентификаторы `SYN-000001`…; префикс
  `SYN-` маркирует клиента как синтетического.
- **`make_display_names(rng, n_clients)`** собирает имена `[SYN] Фамилия Имя` из коротких
  списков узбекских имён и фамилий; для женщин к основе фамилии добавляется окончание
  `-a`. Из-за случайных сочетаний имя может совпасть с именем реального человека,
  поэтому префикс `[SYN]` обязателен, а имена не выходят за пределы `clients.csv`.
- **`draw_latent_profile(rng, n_clients, n_months)`** разыгрывает скрытые черты клиента,
  которые не пишутся в CSV: доход (логнормальный, медиана 5,5 млн UZS), базовый остаток
  (доход × логнормальный множитель), вовлечённость (Beta(5; 1,5)), месяц «ухода» (у 12%
  клиентов) и спящих с начала периода (5%), индивидуальный тренд остатка. Витрина
  должна восстановить сегменты и отток только из наблюдаемых данных.
- **`simulate_monthly_activity(rng, profile, n_months)`** строит матрицы «клиенты ×
  месяцы»: активность (вероятность = вовлечённость, после «ухода» 2%), число операций
  (Пуассон + 1), оборот (число × средний чек ≈ 4% дохода × шум) и остаток (случайное
  блуждание вокруг базового, после «ухода» падает на 30% в месяц). Оборот больше нуля
  тогда и только тогда, когда есть операции.
- **`draw_products(rng, profile, client_ids, months)`** разыгрывает карту, депозит и
  кредит. Вероятность карты растёт с вовлечённостью, депозита с остатком, кредита
  наоборот снижается с остатком. 85% продуктов открыты до периода. Закрытие: 50% для
  ушедших клиентов (в месяц ухода или следующий), иначе 3%. Случайные массивы
  разыгрываются для всех клиентов, чтобы поток случайных чисел не зависел от того, у
  кого какой продукт.
- **`generate_all(seed, n_clients, n_months, start_month)`** запускает всё выше в
  фиксированном порядке на одном `Generator(seed)` и возвращает три таблицы. Требует
  `n_clients ≥ 1` и `n_months ≥ 4`: отток определён только с 4-го месяца.
- **`write_raw(tables, data_dir)`** пишет таблицы в `<data_dir>/<имя>.csv` без индекса и
  с переводом строки `\n`, чтобы байты не зависели от ОС.

### `segment.py`: правила сегментации

- **`tier_by_thresholds(values, affluent_min, premium_min)`** переводит значения в ранг
  0 / 1 / 2 (Mass / Affluent / Premium). Значение, равное порогу, попадает в старший
  ранг.
- **`assign_segment(avg_balance_3m_uzs, declared_income_uzs)`** берёт старший из ранга по
  остатку и ранга по доходу и возвращает название сегмента.

### `mart.py`: витрина client-month

- **`load_raw(data_dir)`** читает три CSV с явными типами: ID и месяцы остаются
  строками, пустой `close_month` становится NaN.
- **`product_holdings(products, months)`** для каждого клиента и месяца возвращает флаги
  `has_<продукт>` и `n_products`. Продукт открыт в месяце `m`, если
  `open_month ≤ m` и (`close_month` пуст или `close_month > m`). Клиенты без продуктов
  в результат не попадают, и `build_client_month` заполняет им `False` и 0.
- **`activity_flags(client_month)`** добавляет `is_active`, `dormant_3m`, `in_churn_base`
  и `new_churn` через сдвиги внутри клиента. Если истории не хватает, значение
  остаётся пустым (NA), а не `False`.
- **`rolling_balance(client_month)`** считает средний остаток за текущий и 2 предыдущих
  месяца. В первых месяцах среднее берётся по доступным месяцам.
- **`build_client_month(clients, products, transactions)`** собирает витрину. Сначала
  проверяет, что у каждого клиента ровно одна строка на каждый месяц и нет неизвестных
  `client_id`; при нарушении бросает `ValueError`. Затем присоединяет доход, считает
  остаток за 3 месяца, сегмент, флаги активности и продуктов. Имена клиентов в витрину
  не берутся.

### `kpi.py`: KPI и миграция

- **`safe_ratio(numerator, denominator, ndigits)`** делит и округляет; при нулевом
  знаменателе возвращает NaN, а не 0 и не ошибку.
- **`group_kpis(group)`** считает все KPI из таблицы выше для одной группы строк витрины.
- **`kpi_by_month_segment(mart)`** вызывает `group_kpis` для каждого месяца: сначала по
  всем клиентам (`ALL`), затем по каждому непустому сегменту.
- **`segment_migration(mart, from_month, to_month)`** строит матрицу переходов между
  сегментами (по умолчанию первый → последний месяц) с долей от исходного сегмента и
  направлением.
- **`migration_summary(migration)`** сворачивает матрицу в итог: число клиентов и доли
  `upgraded_share`, `downgraded_share`, `stable_share`.

### `llm_input.py`: вход для LLM, граница автоматизации

- **`to_json_value(value)`** переводит скаляры numpy и pandas в обычные JSON-значения;
  NaN и NA становятся `null`.
- **`kpi_snapshot(kpi, month, segment)`** берёт из KPI-таблицы только поля
  `LLM_KPI_FIELDS` для одного месяца и сегмента или возвращает `None`.
- **`kpi_delta(current, previous)`** считает разницу «текущий минус прошлый» по каждому
  полю. LLM получает её готовой и не должна считать сама.
- **`assert_aggregates_only(payload)`** бросает `ValueError`, если в payload есть ключи
  уровня клиента (`client_id`, `display_name`, `declared_income_uzs`,
  `end_balance_uzs`), строка вида `SYN-<цифры>` или маркер имени `[SYN]`.
- **`build_llm_payload(kpi, migration, month, min_group_size)`** собирает вход для LLM:
  KPI выбранного (по умолчанию последнего) и прошлого месяца по `ALL` и сегментам,
  разницу, итог миграции, метку `data_origin: SYNTHETIC` и дисклеймер. Сегмент, в
  котором хотя бы в одном из двух месяцев меньше `min_group_size` (по умолчанию 30)
  клиентов, попадает в `suppressed_segments` без чисел. Перед возвратом вызывает
  `assert_aggregates_only`.
- **`load_prompt_template(path)`** читает шаблон `prompts/kpi_commentary_ru.md`; в нём одна
  подстановка `$payload_json`.
- **`render_prompt(payload, template)`** повторно проверяет payload через
  `assert_aggregates_only` и подставляет его в шаблон как JSON. Результат и есть
  полный текст, который ушёл бы в модель.

### `pipeline.py`: полный прогон

- **`sha256_file(path)`** возвращает SHA-256 файла.
- **`write_csv(frame, path)`** пишет CSV с теми же фиксированными настройками, что и
  `write_raw`.
- **`run_pipeline(out_dir, seed, n_clients, n_months)`** выполняет весь конвейер:
  генерация → `data/` → чтение CSV обратно → витрина → KPI и миграция → `mart/` →
  payload и промпт → `llm/` → `manifest.json`. Витрина строится из записанных CSV,
  поэтому прогон заодно доказывает, что её можно пересобрать из `data/` без
  генератора.
- **`main(argv)`** — точка входа `python -m retail_kpi`: разбирает аргументы, запускает
  `run_pipeline` и печатает дисклеймер и список файлов.

## Ограничения

- Распределения подобраны вручную, чтобы выглядеть правдоподобно. Они **не**
  откалиброваны на данных какого-либо банка и ничего не говорят о реальном рынке
  Узбекистана. Выводы о бизнесе на этих числах делать нельзя.

- Все клиенты существуют с начала до конца периода: новых клиентов в середине года нет.
